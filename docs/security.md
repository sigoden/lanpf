# Security Model

This document describes the trust boundaries, threat model and explicitly accepted risks of
`lanfp`. Read the "explicitly accepted risks" section before use.

## Trust Boundaries

| Component | Trust assumption |
|---|---|
| Local user account | Trusted. IPC is accessible only to the current user. |
| Paired device | Fully trusted. Pairing is authorization: it may access any Native TCP port on this machine. |
| Unpaired device | Untrusted. TLS public-key pinning rejects it outright. |
| LAN | Untrusted. All sessions use TLS 1.3. |
| Pairing channel | Relies on the 6-digit code + SPAKE2; does not rely on TLS. |

## Transport Layer

- TLS 1.3 (rustls), only TLS 1.3 enabled, ALPN `lanfp/1`, 0-RTT disabled.
- Both sides use self-signed certificates; the public key in the certificate must equal the
  Ed25519 public key of the pairing record.
- The server (agent port) validates client certificates against the set of known public keys; the
  client accepts only the exact public key of the target device.
- Pinning does not depend on a CA, host names or the system certificate store; certificates are
  merely carriers for public keys.
- Once the session is established, `yamux` is layered on top: one control stream plus one data
  stream per TCP connection.

## Pairing

Flow (B is the device being paired):

```
B: lanfp pair wait                     A: lanfp pair mac-mini@192.168.8.10
         │  <── PairHello(name, uuid, nonce_a, pubkey_a) ──│
         │  ── Challenge(nonce_b, uuid_b, pubkey_b) ──────>│
         │  shows 6-digit code                              │  enters code
         │  <── SPAKE2 msg1 ───────────────────────────────│
         │  ── SPAKE2 msg2 ───────────────────────────────>│
         │  <── AEAD(device info + signature) ─────────────│
         │  ── AEAD(device info + signature) ─────────────>│
         │  <── Done ──────────────────────────────────────│
         │  ── Done (confirms it was persisted) ──────────>│
```

- The 6-digit code is generated by B, has a default TTL of 300 seconds and at most 5 attempts; the
  code is never written to logs.
- The pairing code is the SPAKE2 password. A wrong code yields a different session key, and the
  AEAD check fails, which aborts the pairing.
- SPAKE2 uses the `spake2` crate with the Ed25519 group on both sides. Both devices run the same
  implementation; interoperability with a different RFC 9382 implementation is not a goal.
- The pairing transcript binds both UUIDs, both nonces and both public keys; both sides then sign
  the transcript with Ed25519.
- Both sides do a final Done/Done confirmation; only on success is the `peer` row written and the
  key added to the TLS known-key set.
- A changed public key (device reinstall) is replaced only when the initiator passes `--force`;
  otherwise it is rejected.
- The device being paired must explicitly run `lanfp pair wait` first, otherwise the initiator is
  rejected immediately (exit code 6).
- Only one waiting session is allowed at a time; a second initiator gets "busy".

### Strength of the 6-Digit Code

A 6-digit decimal code has only 1,000,000 possibilities, therefore:

- it is displayed only on the terminal of the device being paired and never sent over the network;
- each `pair wait` allows at most 5 attempts, after which waiting must start again;
- the code expires together with the waiting session;
- SPAKE2 makes offline dictionary attacks infeasible, and online attacks are bounded by the
  5-attempt limit.

## Target Boundaries

- A forwarding target must be a port in the server's current Native inventory.
- Only server loopback addresses are dialed: `127.0.0.1`, `::1`, then the address the port is
  actually bound to.
- Arbitrary `host:port` targets are not accepted, so lanfp cannot be used as a jump host.
- The data stream header carries the internal `rule_id`, which the server uses for logging and
  rejection reasons.

## Local IPC

- Linux/macOS: Unix domain socket, file mode 0600, inside a runtime directory with mode 0700.
- Windows: named pipe `\\.\pipe\lanfp-<username>-<hash>` using the process default DACL (usually
  allowing only the current user and administrators).
- Frame format: `u32 BE length + JSON`, maximum 16 MiB.

## Listener Exposure

- The only listener open to the LAN is the agent port (default `0.0.0.0:47811`).
- Every forwarding listener is forced to bind `127.0.0.1`.
- `lanfp local` / `lanfp remote` hide the local agent port and forwarding listeners.

## Low Ports

- Linux/macOS: a user-level process cannot bind `<1024`. `forward add --listen 80` returns exit
  code 7 and suggests a high port; this version does not guide the user to sudo.
- Native ports below 1024 on the local machine are still listed normally and can still be used as
  **forwarding targets** (the remote side listens on its own high port; the local side only dials
  over loopback).
- Windows: a normal user can usually listen on `<1024`, which differs from Unix behavior.

## Explicitly Accepted Risks

1. **No reject/revoke/allow-list.** Any paired device can create forwards to, and access, any of
   your Native ports. `lanfp inbound` is read-only. Revocation only happens indirectly, by
   deleting the peer's data directory and reinstalling.
2. User-level enumeration cannot see process attribution for other users or separate netns; ports
   are still listed and their owner shows as `-`.
3. mDNS broadcasts the device name, UUID and agent port in cleartext; this contains no keys but
   reveals the existence of the device.
4. There is no code signing on first run, so system security prompts may block it.
5. Windows named pipes rely on the process default DACL and are not further restricted to the
   current user SID only.

If these risks are unacceptable, do not pair untrusted devices.
